# dbt

SQL transformation framework — you write `SELECT` statements, dbt handles the DAG, materialization, testing, and docs.

This is a **monorepo template**: one uv-managed Python environment, one set of dev tooling (sqlfluff, pre-commit), one Makefile, and one shared `profiles.yml` — all serving one or more dbt projects under sibling subfolders. The only project shipped here is [dbt-postgres/](dbt-postgres/), a starter that demonstrates seeds → silver → gold against PostgreSQL.

## Layout

```
dbt/                             ← monorepo root (this directory)
├── pyproject.toml               # Python deps (dbt, sqlfluff, pre-commit)
├── uv.lock                      # generated by `uv sync`
├── .python-version              # Python version pin for uv
├── profiles.yml                 # shared — used by every project below
├── .env.example                 # DB credentials for profiles.yml
├── Makefile                     # task runner (make help)
├── .pre-commit-config.yaml      # hooks: sqlfluff + standard yaml/whitespace
├── .gitignore
│
└── dbt-postgres/                ← one dbt project
    ├── dbt_project.yml          # project name: dbt_postgres
    ├── packages.yml             # dbt_utils
    ├── .sqlfluff                # lint config (dbt templater, postgres dialect)
    ├── models/
    │   ├── silver/              # views in schema `silver`
    │   └── gold/                # tables in schema `gold`
    ├── seeds/bronze/            # CSVs → schema `bronze`
    ├── snapshots/               # example (commented out)
    ├── analyses/                # ad-hoc SQL, compile-only
    ├── tests/                   # singular tests
    └── macros/                  # generate_schema_name override + examples
```

### Why a monorepo

- **One Python env** — `uv sync` once; every project, linter, and hook uses the same `.venv/`.
- **One profiles.yml** — `DBT_PROFILES_DIR` is the monorepo root, so adding a second project (e.g. `dbt-duckdb/`) means a new profile block, not new credential wiring.
- **One task runner** — `make PROJECT=dbt-duckdb build` picks a different project; defaults to `dbt-postgres`.

### The DAG (dbt-postgres)

```
raw_customers  ─┐
raw_orders     ─┼─►  silver_customers ─┐
country_codes  ─┘    silver_orders ────┼─► gold_daily_revenue
                                       └─► gold_customer_lifetime_value
```

## Quick start

Install [uv](https://docs.astral.sh/uv/) once (`curl -LsSf https://astral.sh/uv/install.sh | sh`), then from this directory:

```bash
# 1. Install the env (dbt + sqlfluff + pre-commit, pinned by uv.lock)
make install

# 2. Wire up a database — the postgres/ template in this repo ships matching schemas
cp .env.example .env
set -a; source .env; set +a

# 3. Run the pipeline
make deps        # dbt deps   — installs dbt_utils
make build       # dbt build  — seed + run + test in order

# 4. Browse lineage
make docs        # dbt docs generate && dbt docs serve → http://localhost:8080
```

`make help` lists every target.

### Running a different project

```bash
make build PROJECT=dbt-duckdb   # once you've added a dbt-duckdb/ subfolder
```

### Running dbt directly (no Make)

```bash
cd dbt-postgres
DBT_PROFILES_DIR=.. uv run dbt build
```

## Configuration

All connection details come from the environment via `env_var()` in [profiles.yml](profiles.yml). Copy [.env.example](.env.example) to `.env` and edit.

| Variable | Description | Default |
|---|---|---|
| `DBT_HOST` | Postgres host | `localhost` |
| `DBT_PORT` | Postgres port | `5432` |
| `DBT_DATABASE` | Database name | `app` |
| `DBT_USER` | Role used by dbt — should own bronze/silver/gold | `transform_user` |
| `DBT_PASSWORD` | Password | `transform` |
| `DBT_SCHEMA` | Fallback schema when a model/seed has no `+schema:` set | `bronze` |
| `DBT_SSLMODE` | libpq SSL mode | `prefer` |

### Why the `generate_schema_name` override?

By default, dbt concatenates `target.schema` with any `+schema:` value, so `+schema: silver` on target `analytics` produces `analytics_silver`. This project overrides that macro ([dbt-postgres/macros/generate_schema_name.sql](dbt-postgres/macros/generate_schema_name.sql)) so `+schema: silver` becomes the literal schema `silver` — matching the medallion layout the rest of the repo already uses.

## Linting & pre-commit

`sqlfluff` is configured in [dbt-postgres/.sqlfluff](dbt-postgres/.sqlfluff) with the `dbt` templater so it compiles Jinja correctly before linting.

```bash
make lint          # sqlfluff lint
make format        # sqlfluff fix — review diffs before committing
```

Git hooks live in [.pre-commit-config.yaml](.pre-commit-config.yaml) (standard yaml/whitespace checks + sqlfluff). Install the git hook once:

```bash
make precommit-install
```

Run every hook against every file on demand:

```bash
make precommit
```

The sqlfluff hook uses `language: system` so it shares the uv-managed `.venv/` — the version of sqlfluff pre-commit runs is the same one `make lint` runs.

## Adding another dbt project

To add `dbt-duckdb/` as a sibling:

1. `mkdir dbt-duckdb && cd dbt-duckdb && uv run dbt init` (or copy `dbt-postgres/` and rename).
2. Change the adapter in [pyproject.toml](pyproject.toml) (`dbt-duckdb`) and `uv sync`.
3. Add a `dbt_duckdb:` profile block to [profiles.yml](profiles.yml), pointing `profile: 'dbt_duckdb'` in the new project's `dbt_project.yml`.
4. Extend the pre-commit `files:` regex and sqlfluff paths to cover the new folder.
5. `make build PROJECT=dbt-duckdb`.
